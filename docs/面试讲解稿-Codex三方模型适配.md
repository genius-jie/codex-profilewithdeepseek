# 面试讲解稿：Codex 三方大模型无缝适配项目

> 用途：面试时讲解「这个项目是干嘛的、我做了哪些工作、碰到什么问题、怎么解决的」。
> 用法：第一部分直接背；第五部分挑 4～5 个案例讲；第七、八部分对付追问。

---

## 一、60 秒版（开场直接说这段）

我做的是一个「让 Codex 这个 Agent 客户端能无缝切换各家大模型」的适配项目。

我的主力开发工具是 Codex，它原生只服务 OpenAI 自己的模型。我想在里面直接调用 DeepSeek、智谱、千问、Kimi 这些国内外最强的模型，但真正接进去之后发现：每家的输入字段、返回格式、流式事件、工具调用语法都不一样，官方客户端根本不认，动不动就报错、卡死、任务中断。

所以我在客户端和模型之间做了一层**协议适配代理层**，把各家模型的差异在中间抹平。这个项目就是我长期做这层适配的积累：一共修了 9 大类、几十个具体的兼容故障，核心代理脚本迭代到第 39 版，配套一套自动化回归测试，并且用真实模型做过跨模型切换验证。

一句话总结：**客户端只会说 OpenAI 那一套话，上游各家只会说自己那一套话，我在中间当翻译，同时保证翻译完之后客户端能用、模型的行为也正常。**

## 二、3 分钟版：项目背景 + 我的角色

### 项目要解决的真实问题

现在做 AI 开发的人普遍有这么几个痛点：

1. **成本与可用性**：官方模型贵、国内访问不稳定，大家想用国产的强模型（DeepSeek 这类推理和代码能力很强的，千问、Kimi 这类长上下文多模态的）。
2. **接进去就崩**：三方模型直接对接 Codex 会出各种问题——字段名不一样被网关拦截、协议不一样直接 502、工具调用格式不一样导致执行报错。
3. **没有统一的工程治理**：用哪个模型、怎么配、出问题怎么排查，全靠试，没有沉淀。

我这个项目就是把「在 Codex / Codex++ 里稳定使用三方模型」这件事，做成一套可复用、可验证、有故障案例库的工程方案。

### 我在里面实际承担的工作

| 工作块 | 具体做了什么 |
|---|---|
| **协议适配层开发** | 写并长期维护核心适配代理（2200+ 行）：新老协议双向转换、流式事件重组、字段映射、ID 规范化 |
| **工具调用兼容** | 修三方模型工具调用的字段漂移和格式信封问题，让「执行命令」这类内置工具在三方模型下能正常跑 |
| **模型行为纠偏** | 解决三方模型「说一句就停」和「停不下来」、思考档位不跟随界面设置等自主行为问题 |
| **稳定性与运维** | 加超时看门狗、终止事件；把代理做成 Windows 服务（崩溃自重启）；健康端点带版本校验；启动守卫自动检查代理是否挂上 |
| **测试与回归** | 写 6+ 个自动化回归脚本、16+ 用例；假上游做协议边界回归 + 真实模型跨模型切换验证 |
| **迁移与沉淀** | 整理 3 个宿主（普通 Codex / Codex++ / Claude Code）的换机迁移包；沉淀 9 大类故障案例文档 |

## 三、架构：一句话讲清数据怎么走

`Codex 客户端（Codex++） → 本地协议适配代理（15740） → 本地模型网关 CodexManager（48760） → 上游各家模型 API`

三个关键点，面试时说出来就够了：

1. **最左边**：官方客户端，闭源改不了，它只会说 OpenAI 那套协议。
2. **中间那一层是我加的**：负责把客户端的话翻译成上游听得懂的，再把上游的回复翻译回客户端认得的；同时负责修 ID、解包工具参数、过滤脏数据。
3. **最右边**：本地网关统一转发到各家模型 API。原生 GPT 链路完全不动，还是直连官方账号池——这是隔离设计，改三方模型不会影响原生模型。

## 四、我做了什么：按「我改了什么」组织

- 我写了一个**常驻反向代理**，客户端所有请求先过我这一层。
- 我在这一层里实现了四个核心能力：
  1. **ID 规范化**：把三方模型不规范的调用 ID 改成客户端要求的格式（请求、响应两个方向都改，且关联字段同步改）。
  2. **协议双向转换**：新版协议和聊天补全老协议之间的互转，包括整个流式过程的状态机。
  3. **工具参数解包与字段归一**：把上游包错的 JSON 信封解开，把写错的字段名（比如命令工具该写 `cmd` 却写成 `command`）纠正过来。
  4. **脏数据过滤**：剔除空的思考块、把碎片化的文本块合并、清理历史里混进来的图片等。
- 我给它配了**回归测试**：用假上游验证协议边界，用真实模型验证端到端，用健康端点验证版本号（防止对着旧进程调试）。
- 我把它做成了**Windows 服务**：崩溃自动重启，重启脚本会校验适配器版本，启动入口有守卫检查代理有没有挂上。

## 五、重点案例：问题 → 根因 → 怎么修

> 讲法建议：每个案例按「现象（面试官能听懂）→ 排查过程 → 根因一句话 → 修复 → 我的收获」来。
> 案例 7、8、5、3 最出彩，优先讲。

### 案例 1：一换模型就报 ID 格式错误

- **现象**：切到三方模型后，客户端立刻弹 `Expected an ID that begins with 'ctc'`，对话进行不下去。
- **排查**：抓请求和响应体对比，发现 OpenAI 新接口要求工具调用的 ID 必须以 `ctc_` / `fc_` 开头，而三方模型返回的全是 `msg_` 开头。
- **根因**：ID 的命名规则是 OpenAI 的私有约定，三方模型不知道也不遵守。
- **修复**：在代理层做双向改写——请求方向把客户端发来的 ID 规范化后送上游；响应方向把上游的 `msg_` 改回 `ctc_` 再给客户端。关键是**关联字段要同步改**：改了 `tool_call.id` 就必须同步改引用它的 `tool_call_id`，否则校验会报「引用不匹配」。
- **我的收获**：一条通用原则——**改主体必须同步改引用**。分布式和协议层到处是这种坑。

### 案例 2：切到 DeepSeek / Kimi 直接 502

- **现象**：换到 DeepSeek 或 Kimi，请求秒失败，报上游错误 502。
- **排查**：先怀疑密钥、余额、服务商故障，全部排除；然后用同一把密钥对比不同端点，发现网关**只开放了聊天补全老接口**（`/v1/chat/completions`），**没有新版接口**（`/v1/responses`）。
- **这里有个关键判断**：502 不等于服务商挂了。账单页面没有计费记录，说明请求没跑完，但不代表请求没发出去。判断故障时要区分「服务商故障」和「协议端点不匹配」。
- **根因**：客户端说新协议，上游只有老协议，中间网关不做转换。
- **修复**：在代理层自己实现双向协议转换（`responsesToChat` / `chatToResponses`），并且把老协议的流式返回重新拼装成新协议的流式事件（一个 SSE 状态机）。
- **我的收获**：要分清网关是在「透传」还是在「转换」；没有现成转换能力时，自己在兼容层实现是可行解。

### 案例 3：执行命令工具报 JSON 语法错误

- **现象**：三方模型调用「执行命令」工具时，客户端报 JavaScript 语法错误 `Unexpected token ':'`。
- **排查（这里走过弯路）**：一开始我以为是模型写的代码有问题，往代码内容上查了很久，一直没结果。后来把真实落入会话记录的数据 dump 出来看，才发现上游传过来的参数是 `{"data":"1+1"}` 或 `{"arguments":"text(1 + 1)"}` 这种「JSON 信封」，而正确的形式应该是**裸的 JS 文本**。那个 JSON 里的冒号被当成 JS 代码送进求值器，当然报错。
- **关键判断**：这个错误**时有时无、和内容无关**——这种特征说明是**序列化层的 bug**，不是内容复杂或转义问题。用「同一形式、不同内容」做对照实验，就能快速证伪「内容归因」。
- **修复**：在适配边界按工具名解包——**只对命令执行工具解包，其他工具原样保留**（解包过头会把补丁类工具改坏）。
- **我的收获**：查「间歇性、无规律」的 bug，要往协议/序列化层想，别先往内容上想。

### 案例 4：修完了却不生效——流式协议少了一个空格

- **现象**：上面的解包逻辑写完了，日志显示处理过了，但错误照样出现。
- **排查**：抓响应流，发现上游发的是 `data:{...}`（冒号后面**没有空格**），而我的匹配逻辑只认 `data: {...}`（有空格）。流式协议规范里这两种都合法，我漏了一种。
- **后果**：因为全都不匹配，响应方向的事件**一个都没被改写**——静默失效，日志还看得出「处理过」。
- **修复**：两种前缀都匹配，同时把关联的 item 标识也一起规范化。
- **我的收获**：①这是个单字符 bug，最容易被漏；②**「流量经过代理」不等于「处理生效」**——必须验证输出结果（看输出的 ID 是不是真的变了），不能只看日志有没有打印。

### 案例 5：上下文压缩报错，列号 144 —— 假响应比报错更危险（强烈推荐讲）

- **现象**：对话到一定长度触发自动压缩时报错，错误里带了个列号 144。
- **排查**：这个数字是关键线索——**它正好等于我代理伪造的那个响应体的字节长度**。意思是：客户端把整个响应体读完了，都没等到它需要的字段。
- **根因**：我代理拦截了压缩请求后，自己造了一个「压缩成功」的假响应，但字段没给全，缺了客户端解析必需的字段。它伪装成 200 成功，比直接报错还难查。
- **修复**：按客户端期望的标准响应结构把字段补全；更彻底的方案是——**不再伪造压缩，改成原样透传，压缩不了就让上游显式报错**。
- **我的收获（我最看重的一条）**：**显式失败 > 静默成功**。假响应会让上游消费者做出错误决策：客户端以为压缩过了，其实没压，会话一路膨胀到 1MB 上限直接崩。宁可让用户看到一句「这个功能不支持」，也不要让他不知情地走到崩溃。

### 案例 6：切换后请求秒断，「消息列表为空」

- **现象**：切到 DeepSeek / Kimi，请求发出去立刻失败，说消息列表是空的；但同样操作切千问却没事。
- **排查**：对比两条代码路径才发现——千问走的是**透传**（不转换），DeepSeek / Kimi 走的是**协议转换函数**。而转换函数只认旧版客户端的输入格式，新版客户端改了格式，结果这些输入项被**静默丢弃**，转换完之后消息列表就空了。
- **根因**：适配函数对新旧输入格式兼容不全，而且丢弃的时候没有任何提示。
- **修复**：兼容三种输入形状。
- **我的收获**：①**「静默丢弃」比报错更危险**——转完为空请求照样发出去，伪装成上游问题；②同一个代理里不同分支（透传 vs 转换）必须分别验证，「千问是好的」不能证明「DeepSeek 也好」。

### 案例 7：Kimi「说一句就停」，然后又被我治成了「停不下来」（最能体现迭代思维）

- **现象 A**：让 Kimi 干活，它调完一个工具，播报一句「我接下来要做什么」，然后**就结束了**，不再继续调工具，任务卡在半路。
- **排查**：先看模型停止的原因字段——它返回的是「模型选择停止」，不是「模型要调工具」。这一下就区分开了：这是**模型行为问题**，不是链路问题。
- **尝试 1（失败）**：我在工具描述里加了一句「返回后禁止只播报就停」。Kimi **无视**了——它播报的内容里明明写了下一步要干什么，还是选择停。说明：对强指令跟随的模型讲「软契约」没用。
- **尝试 2（成功）**：改成在协议层用「必须调用工具」的**硬约束**，模型绕不过去。
- **现象 B（新问题）**：硬约束加上之后，Kimi 活干完了还在**不停地调无意义的命令**，15 秒一次无限循环。
- **根因**：我加的强制续跑是个「粘滞开关」，**没有退出条件**。
- **修复**：用「上一轮是纯工具轮（只有工具调用、没有文本输出）」当退出信号——干完活没话说就允许自然停止；一旦有文本输出（说明它在跟用户对话）就继续强制调工具。
- **我的收获**：①**「描述写对」不等于「模型行为合规」**，测试只验文本不验行为 = 假绿；②强制和允许停止是一对张力，**加硬约束必须同时设计进入条件和退出条件**，否则就从「停得太早」变成「停不下来」。

### 案例 8：界面选了思考档位，模型还是按默认跑

- **现象**：界面上把思考强度拉到最高，模型表现没变化。
- **排查（三步）**：①先看代理日志里传给上游的思考档位参数是不是跟着界面变——发现**协议转换时这个参数被丢了**，没映射过去；②再看模型目录里这个模型声明支持哪些档位——发现有模型写的是**空数组**；③空数组的语义不是「用默认档」，而是「**这个模型不支持思考档位**」——客户端一看不支持，界面滑块直接不显示，全局默认也被忽略。
- **修复**：协议转换时逐字段映射；模型目录里把支持的档位显式列出来。
- **我的收获**：**参数丢失是静默的**——用户感知不到，但效果打折。协议转换时要把客户端发的每个参数逐个核对是不是都到了上游。

### 案例 9：上游卡死，客户端永久转圈

- **现象**：偶尔上游不响应，客户端就无限转圈，新会话也排不上队。
- **排查**：日志里只有「请求入队」没有「请求出队」，说明请求挂死了。实测一个请求挂了 70 分钟不释放，队列从 7 个堆到 11 个。
- **根因**：两个缺口——①代理转发用的底层 HTTP 客户端**默认没有超时**；②超时后只关了连接，**没有给客户端发终止事件**，客户端的解析器一直悬着等下一段。
- **修复**：①加两段式看门狗（首字节 120 秒超时 + 空闲 300 秒超时，每收到数据就重置）；②超时或出错时补发标准的失败终止事件。
- **我的收获**：代理转发必须带超时和终止语义，否则上游一挂，整个客户端就废了。

### 案例 10：会话悄悄膨胀，撞上 1MB 上限

- **现象**：长会话用着用着突然报错，超出字符上限。
- **根因**：就是案例 5 那个假压缩——客户端以为压缩过了其实没有，历史一直在增长，最后撞上限。
- **修复**：移除假压缩拦截。
- **二次教训**：**移除拦截不等于修好了**。改完之后发现压缩请求还会经过另一个处理函数，那个函数把请求体结构破坏了，最后得让压缩请求**完全旁路**。
- **我的收获**：「不再拦截」不等于「不再处理」——移除一个分支后，要追查请求还会不会流经其它层。

## 七、方法论沉淀（最能打动面试官的部分）

1. **查「间歇性、无规律」的 bug，先怀疑协议和序列化层**，别往内容复杂度上想。
2. **假响应比报错更危险**：显式失败 > 静默成功。
3. **静默丢弃比报错更危险**：转换后为空还照样发请求，会伪装成上游故障。
4. **改主体必须同步改引用**（调用 ID ↔ 引用 ID）。
5. **单字符、单字段的差异最容易被漏**：流式协议的空格、字段取空数组的语义。
6. **软契约不等于硬约束**；加硬约束必须同时设计**退出条件**。
7. **「经过代理」不等于「处理生效」**：要验证输出结果，不能只看日志。
8. **透传路径正常不等于适配路径正常**：同一层里不同代码分支要分别验证。
9. **报错信息里的数字常常是线索**：列号正好等于响应体字节长度，说明是字段缺失，不是网络中断。

## 八、可能的追问 & 回答要点

**Q：为什么要在中间加一层代理，不直接改客户端？**
A：客户端是官方闭源客户端，改不了；上游网关也不做协议转换。中间这层是唯一能做适配的位置。而且加在中间还有个好处——原生 GPT 链路完全不受影响，还是直连官方账号池。

**Q：你怎么保证改完不影响原生模型？**
A：按模型来源隔离。协议转换只对走老协议的 DeepSeek / Kimi 这类生效，GPT 原生的路由完全不动。每次改完都跑回归，并且验证 GPT 原生的请求来源还是官方账号池。

**Q：这些改动你怎么证明真的生效了？**
A：三层验证——①用假上游（最小的流式响应样本）做协议边界回归，把「适配逻辑问题」和「上游可用性问题」分开；②真实模型端到端回归（13 轮切换）；③健康端点校验适配器**版本号**。第三点是踩过坑才加的：旧进程占着端口，新代码静默不生效，你以为在调新代码，其实在看旧进程的输出。

**Q：你觉得这层适配最容易出问题的地方在哪？**
A：三处——①流式协议的事件形状（最容易漏单字符差异）；②工具调用的关联 ID；③请求参数在协议转换中的静默丢失。

**Q：做这个项目你最大的收获是什么？**
A：一句话——**别让失败静默发生**。我修过的坑里，最难查的不是报错，而是那些「假装成功」的：假压缩、静默丢弃、响应事件没被改写。所以后来我的原则是：宁可显式报错，也不要静默通过。

**Q：这个项目最难的地方是什么？**
A：没有文档。上游模型和网关的实现细节都是黑盒，只能靠抓包、对照实验、字节级取证一点点还原真实行为。比如「列号 144」这种线索，是靠本地复现响应体、量字节长度才对上的。
