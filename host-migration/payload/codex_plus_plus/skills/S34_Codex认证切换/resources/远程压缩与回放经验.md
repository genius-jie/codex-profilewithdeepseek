# Codex++ 远程压缩与跨模型回放经验

本文件是 S34 的按需参考，详细记录 2026-09-27 前后 DeepSeek/Kimi/GPT-6A 兼容故障的共同根因。它不创建新的运行入口、状态库或控制面。

## 1. 真实调用链

```text
Codex++ -> http://127.0.0.1:15740/v1
        -> CodexManager 127.0.0.1:48760
        -> provider
```

Codex++ 的 remote compaction v2 走普通 `/v1/responses`，请求最后追加：

```json
{"type":"compaction_trigger"}
```

核心会检查响应中是否有且只有一个 `type: "compaction"` 输出项。旧适配器将请求转成 Chat 后只返回 reasoning/message，导致 `got 0 from 2 output items`。

## 2. 三个必须同时修复的协议不变量

### 压缩输出

Chat-only 模型的压缩请求必须在现有适配入口内完成：追加明确的摘要指令、关闭工具调用、保留历史消息，并将 Chat 响应转换为唯一 `compaction` 输出项。空 compaction、假成功和静默 no-op 都会让上下文继续膨胀。

### 私有项回放

适配器自己的压缩项带 `cmp_` ID，只能作为内部摘要载体。回放给原生 Responses 或不接受私有 compaction 的 provider 时，必须转换为普通 assistant message，并生成新的 `msg_` ID：

```json
{
  "type": "message",
  "id": "msg_<uuid>",
  "role": "assistant",
  "content": [{"type":"output_text","text":"[Previous context summary]..."}]
}
```

`cmp_` 不能复用为 message ID；assistant 消息不能使用 `input_text`，否则会分别触发 ID 校验错误和 `Supported values are output_text and refusal`。

### 模型与推理选择

UI/state 中的手动模型和 reasoning effort 是当前线程的事实。Codex 核心的 `ModelDownshift` 可能在预压缩阶段调用历史模型；适配层应兼容该意图，不要硬编码全局模型。`reasoning.effort` 到 Chat provider 的 `reasoning_effort` 映射必须保留，尤其是 `max`/`ultra`，否则最高思考等级会表现为没有生效。

GLM-5.2、GLM-5.3、GLM-5.3-Flash 也遵循同一合同。模型目录的 `supported_reasoning_levels`、15740 的 Chat-only 路由和 `reasoning_effort` 转发必须同时存在；只补目录会出现 UI 有等级但 CodexManager 日志仍为 `reasoning=none`。GLM 的 Chat 上游使用现有 `/v1/chat/completions` 适配入口，避免 Responses 历史工具项直接落到不兼容的第三方 Responses 路径。图片能力单独由模型目录的 `input_modalities` 声明控制：当前只把已验证的 `glm-5.3-flash` 标成 `text,image`，GLM-5.2/5.3 维持 `text`。

2026-09-28 的模型能力审计确认：Qwen 3.8 Max/Flash 直连 active A2Agent 时，使用合规尺寸图片均返回 HTTP 200；此前的 502 来自仍被 ordered 策略选中的 disabled `omnimodel.me` 路由。同步脚本会保留 Qwen 的 `text,image` 能力声明，正式路由必须收敛到 A2Agent。

同一轮审计覆盖了当前 Codex++ 目录里的全部第三方模型。模型是否进入 `input_modalities=["text","image"]` 只由下面的证据决定：

| 模型 | 当前目录 | 证据口径 |
| --- | --- | --- |
| `glm-5.3-flash` | `text,image` | A2Agent 目录标为 vision；本机 Chat 请求曾返回 HTTP 200；15740 的 Responses→Chat 回归通过 |
| `kimi-k3` | `text,image` | A2Agent 目录标为 vision；本机 15740 真实请求返回 completed |
| `deepseek-v4-pro` | `text,image` | 原生 Pro 图片会被上游拒绝；15740 对含图请求稳定路由到 `deepseek-v4.1-flash`，因此这是 Codex++ 适配能力 |
| `deepseek-v4.1-flash` | `text,image` | 作为 DeepSeek 视觉路由目标，历史真实请求返回 HTTP 200 和工具调用 |
| `glm-5.2`、`glm-5.3` | `text` | A2Agent 目录标为 coding；没有视觉证据 |
| `qwen3.8-max`、`qwen3.8-flash` | `text,image` | A2Agent 直连 16×16 PNG 均返回 HTTP 200；CodexManager 必须禁用旧 `omnimodel.me` route 后再走现有 Chat 适配 |
| `kimi-k2.7-code`、`deepseek-v4-flash`、`MiniMax-M3`、`qwen3.8-max-0902` | `text` | 当前目录/上游没有可复核的视觉支持证据；普通 HTTP 200 或能接受字段不等于模型真正识图 |

因此“多模态”不是按厂商或模型名字批量推断，而是按当前实际消费者和真实上游证据逐项收敛。正式生成源是 `@@LAUNCHER_ROOT:win@@\Sync-CodexPlusPlusModelCatalog.ps1` 的 `image_input_modalities` 映射；手工改 D 盘缓存会在下次启动同步时被覆盖。

## 3. 运行态加载不变量

2026-09-29 新增 DeepSeek 长会话边界：CodexManager 对单次输入硬限制为 `1,048,576` 个字符。实测 DeepSeek 会话在约 418k tokens 时已经生成约 2.25MB 的 Responses 请求、约 1.5–1.8MB 的 Chat 转换请求，旧的 `auto_compact_token_limit=900000` 触发过晚，导致 `input_too_large`。正式模型目录现将 `deepseek-v4-pro` 的自动压缩阈值前移到 `160000` tokens；该值只改变现有 remote compaction 的触发时机，不截断历史、不新增旁路流程。同步脚本更新模型预算字段时保留现有能力、推理和路由元数据。

源码版本、重载脚本、服务 `/health` 和实际进程必须一致。修改 JS 后：

1. 跑 `node --check` 和 loopback 协议回归；
2. 用管理员 PowerShell 重载 `CodexIdSanitizer`；
3. 核对 `/health` 的 adapter 版本和 Node 进程创建时间；
4. 必要时走官方 `Start-CodexPlusPlus.ps1 -Restart`，确认 D 盘 profile、主进程和线程模型未漂移；
5. 再触发真实长会话压缩。

源码文件存在、离线测试通过或服务端口可访问，都不能单独证明运行中的进程已经载入新代码。

## 4. 同类问题的统一边界

- 正常 `/v1/responses` 路径保持原样；只在已有 15740 适配器内处理第三方协议差异。
- Kimi 的工具批次、单飞队列、客户端断开释放、SSE error 终态和 reasoning 摘要事件继续沿用现有适配逻辑。
- 旧会话的 `rs_` summary-only reasoning、`item_reference`、`cmp_` compaction 和历史工具 ID 必须按各自协议字段处理，不能用统一前缀替换掩盖语义差异。
- 普通 Codex、C 盘官方账号和普通配置不在修复面；Codex++ 的 mutable data 仍只归 D 盘 profile。
- 不新增第二套压缩流程、旁路服务、watcher、持久状态库或模型注册表。

## 5. 证据口径

本轮的关键回归包括：compaction 输出数量为 1、`cmp_` 转 `msg_`、assistant 内容为 `output_text`、Kimi 工具消息、Kimi continuation、GPT 模型切换。当前目标运行版本为：

```text
responses-summary-v39-qwen-vision-v1
```

真实长会话尚未触发新的压缩时，只能报告“适配器已加载并通过定向回归，真实压缩待触发”，不能把 loopback 结果写成完整客户端验收。
