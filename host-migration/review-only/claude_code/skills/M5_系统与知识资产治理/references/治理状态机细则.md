# M5 系统与知识资产治理细则

本文件描述 M5 的治理检查职责，不定义运行状态机，不替项目 Runtime 管理任务、checkpoint 或业务数据。

## 1. 三层归属

- 父级 `.agent`：跨项目 Constitution、Rule、Skill、Workflow、Methodology 与全局索引；
- 子级 `.agents`：本仓库的 orchestration 采用说明、域入口和 repo-local SOP；
- 当前项目：业务代码、PRD、设计、测试、运行证据和项目专属契约。

跨层内容按用途拆分并互相引用，不复制另一层的权威正文。项目事实不能漂进父级法典，父级方法也不能被某个项目实现路径绑死。

## 2. 治理对象检查

对 Skill、Rule、SOP、Workflow、Index、Reference、Constitution 的 CRUD，检查：

1. `GOVERNANCE_OBJECT_CRUD_GATE` 是否说明对象类别、动作、SSOT、层级、注册同步与影响面；
2. frontmatter 护照与 `birth_ceremony_id` 是否有效；
3. `related/extends/children` 是否指向真实资产；
4. 新门类是否已有唯一 SSOT，能否只写本地采用层；
5. `doc_status` 与父/子索引是否同步；
6. 活动入口是否仍指向已归档实现；
7. 变更知识图谱或预加载关系时是否提供 `KNOWLEDGE_GRAPH_CHANGE_RECEIPT`。

## 3. 当前项目产物边界

- 先确认用户指定或项目声明的 `project_root`；
- 使用当前 request artifact refs、显式交付目录或项目自有 manifest 契约；
- 项目没有统一 workspace/manifest 时，不为治理方便创建通用运行布局；
- audit/review 证据必须能被当前消费者读取，但不得硬编码旧仓目录；
- 运行缓存、临时验证目录和业务持久数据由当前项目自身的生命周期策略治理。

M5 只报告越界、孤儿、断链、污染与可归档候选。删除、移动或批量归档必须获得用户明确授权并先验证精确目标。

## 4. 新版 Automation Core 存储边界

E Automation Core 的项目级存储只通过其公共 `storage inspect/archive` 能力显式检查或归档。M5 不建立 TTL/vacuum cron，不手删 WAL/SHM，不直接修改 Core SQLite，也不把旧 D 的清理脚本迁回新版。

## 5. 出口证据

M5 输出：检查范围、observed facts、risk inference、unknowns、受影响索引、建议处置（保留/外移/归档/删除候选）以及需要人类决定的事项。建议不是自动执行命令。

## LEGACY_CONTROL_ARCHIVE_ONLY

旧统一 `docs/specs/<slug>` 布局、旧 artifact workspace API、固定目录映射、全域 7 天 TTL、自动删除 review、旧治理状态机与旧 D 清理脚本仅作历史参考。当前任务不得调用这些机制或把它们作为新版项目的硬前置条件。
