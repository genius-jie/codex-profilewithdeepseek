## 域专属错题本

### 坑位 1：检查清单闭门造车导致审计权威性不足

*   **【反例】**：
    P2.6 红队评审的检查清单是 Agent 凭直觉拍脑袋写的，没有标注每条规则的知识图谱出处。
*   **【后果】**：
    蓝队（P1/P2/P2.5）收到驳回意见后质疑"这条规则出处在哪？"，红队无法举证，导致评审结果缺乏权威性，蓝队不愿改。
*   **【正例（SOP）】**：
    P2.6 的每条检查项必须标注来源文件路径（如 `architecture.md §1`、`P4 SKILL.md 坑位 15` 等）。必须先全域扫描 `.agent/assets/references` + `.agent/assets/rules` + 同类 S/M 级技能，再据实萃取规则。

### 坑位 2：首轮审计全 PASS 的"老好人"倾向

*   **【反例】**：
    P2.6 首次收到蓝队初稿后，因为文档写得"看起来不错"，就逐条打了 PASS 放行。
*   **【后果】**：
    蓝队对自审的过度自信没有被打破，潜在缺陷被带入下游。P2.6 的存在变得没有意义——成了一个"橡皮图章"。
*   **【正例（SOP）】**：
    首轮魔鬼必究法则（Devil's Advocate）：首次对未经红队打回过的蓝队初稿，绝对禁止全部 PASS。必须主动找出至少一个遗漏/边界/证据盲区进行驳回，强行逼迫蓝队二次加固。

### 坑位 3：P 系上游未经 P2.6 审核就直接往下传

*   **【反例】**：
    P1/P2/P2.5/P3 完成交付物后直接往下游传，跳过了 P2.6 红队评审。
*   **【后果】**：
    质量门形同虚设，下游拿到的可能是有重大遗漏的图纸或 task.md。
*   **【正例（SOP）】**：
    `execution.md` 全局 AOP 闸门已强制要求所有 P 系握手 JSON 中必须包含 `p26_review_verdict.status = PASS` 字段。下游入口（如 P3 的 BLUEPRINT_ANALYSIS）必须校验该字段，缺失或非 PASS 一律拒收。

### 坑位 4：盲目信任 Grep 搜索产生的假阴性判定 (Anti-Grep Illusion)

*   **【反例】**：
    P2.6 在审查配置清单（如 `jobs.json` 中的 cron ID 或 UUID）时，直接使用 `grep_search` 搜索特定片段，收到 `No results found` 后立刻下结论“配置丢失/未挂载”，并以此驳回上游交付物。
*   **【后果】**：
    由于底层环境的编码差异、JSON 跨行格式限制、或 UUID 带转义等问题，纯文本模糊搜索极易产生“假阴性”误杀。这严厉违背了“无验证不完成”铁律，将严谨的审计变成了捕风捉影。
*   **【正例（SOP）】**：
    当核心判定依赖于审查**结构化配置文件**（JSON / YAML / Markdown Header 等）的内部确凿细节时，绝对禁止以底层模糊文本检索的结果作为裁决依据！必须亲自投递能够完整加载解析该文件的 Python 验证脚本，用程序级的精确逻辑结构进行提取验证（Script-Assisted Verification）。

## [2026-04-11] 死链物理检测铁律 + 角色扮演走查法 + 证据最低门槛
- **症状**：P3 引用了不存在的文件导致卡死；P4 YAML 头部语法破损；S 层回执用"已验证"两个字就糊弄过关。
- **病因**：审计只看格式不看实质，缺乏物理验证机制和换位思考推演。
- **解法（三把刀）**：
  1. **死链物理检测**：任何 Skill 中引用路径，审计时必须用 Test-Path 物理验证存在性
  2. **角色扮演走查**：审计 P 级 Skill 时，假装自己是下游 Agent，从第一个 State 走到最后一个，每步拷问"手上信息够不够盲写正确架构？"走不通即判挂
  3. **证据最低门槛**：回执字典必须含结构化证据（curl 返回体、AST 分析树等），严禁采信口头担保

## [2026-04-16] P2.6 审计弹匣与上游版本脱节
- **症状**：P2.6 的 84 条检查项中有 6 条与上游 Skill 最新版不同步。P1 新增了 First-Fact Doctrine，P2 新增了三级举证深度标尺，P3 新增了 S14 物理验证卡口——但 P2.6 弹匣全部停留在旧版。
- **病因**：P2.6 作为下游审计者，没有建立与上游被审对象的版本联动机制。
- **解法**：每次 P1/P2/P3/P4 发生重大版本更新后，W7 应自动触发 P2.6 弹匣同步检查。
- **铁律**：审计工具的版本必须 >= 被审对象的版本，否则审计结果无效。

## [2026-04-16] M12 式防偷懒机制推广到审计场景
- **症状**：P2.6 有 ✅/❌/⚠️/🔍 标记体系，但缺少物理强制层——模型可以在脑内"自审过了"但实际遗漏。
- **病因**：审计只有软约束（标记体系），没有硬物理中断。
- **解法（三条新攻击纪律）**：
  1. Progress Anchoring：逐条即时输出审计结果，不允许批处理
  2. BLOCKED Guard：证据不足时阻断，不允许跳过
  3. Checkpoint Snapshot：每 5 条输出中间快照
- **推广范围**：S13 代码审查、W9 出口验收等所有需要逐条走查的场景。

## [2026-04-16] "谁来审计审计者"架构盲区
- **症状**：P2.6 是系统唯一不挂载 W9 出口验收的 P 级资产。所有其他 P 级技能都有 W9 终审联动，唯独 P2.6 自身"豁免"了被审计。
- **病因**：审计者的自审通道是软约束（写不写全靠模型自觉）。
- **解法**：
  1. 强制自省最低门槛：每次审计必须输出至少 1 条清单进化建议
  2. W9 最低限度自审：审计报告必须自检五节完整性
  3. 修复 P2.6 与 M9/asset-governance-audit-protocol 之间的双向图谱断链

## [2026-04-16] P2.6 与 M9 路由混淆：审业务交付物 ≠ 审系统基石资产
- **症状**：本轮起初用 M9（系统基石巡检）去审 P2.5 的 implementation plan，被指挥官纠正为 P2.6。
- **病因**：两者都叫"红队审计"，但靶向完全不同——M9 审 `.agent/assets/rules/skills/workflows` 系统基石，P2.6 审 PRD/Tech Spec/task.md 业务产物。路由表描述不够醒目。
- **解法**：在 W1 路由触发词表中明确区分：
  - "审计交付物/审 PRD/审 Tech Spec" → P2.6
  - "审计系统资产/审 Skill/审 Workflow" → M9

## [2026-04-16] DAG 开发依赖顺序 ≠ 运行时数据流方向
- **症状**：审计 P2.5 的 DAG 时，把 `M202 → M301 → M203` 判为"方向画反了"。
- **病因**：混淆了"谁先编码"（开发依赖）和"数据从哪流向哪"（运行时数据流）。M203 是主控，需要 M202 和 M301 先开发好才能组装，所以排在最后是正确的。
- **解法**：审 P2.5 的 DAG 时，第一步必须先确认 DAG 的语义是"开发依赖顺序"还是"运行时数据流方向"。两套顺序可以完全相反。
