# S19 日报合并铁律与约束指标

> 由 S19 SKILL.md 外置。完整合并规则、约束指标、质量硬规则见正文。

## 2. 核心原则
- **四源全局扫描硬规则**：以后写日报必须按今天纠偏后的标准执行：全局扫描 Antigravity、VSCode Claude Code、Codex++、独立 Codex 四类当天会话源，必要时再补扫 `.gemini/.antigravity/.claude/@@PROFILE_REPO:win@@/@@CODEX_HOME:win@@` 等真实会话目录；不能只依赖预采集摘要、cron 结果或 git 变更。若任一源头未确认扫描，必须在生成前继续深挖或向用户明确说明证据边界，不得假装已扫全。
- **四源闭环回执硬门**：正式日报生成前，必须在 evidence 中形成 `source_coverage` / “四源采集回执”区块，逐项列出 Antigravity、Codex++、独立 Codex、VSCode Claude Code 的扫描状态、根路径、文件数、用户输入条数、失败/空结果说明；任一入口不是 `scanned` 或 `scanned_with_warning` 时，不得宣称全量采集完成。
- **用户补充事实优先定稿**：当用户当天补充了人名协作、工作交接、APP 手测、生产环境变更等真实事项时，必须作为高优先级事实锚点纳入候选工作版图；若本地会话命中不足，应标注为“用户当日补充事实”并继续回源头找证据，不能因为自动采集没命中就丢弃。
- **漏项维度强制核对**：日报正文前必须额外核对四类高漏项：①人名协作与新用户开通；②项目/工程交接与后续接手；③APP 手测业务链路与新老用户差异；④生产环境资源、中间件、公网连接回收和服务回归。任何一类被用户提到或会话命中，都必须进入候选条目审计表。
- **三入口用户输入流优先**：日报第一事实源固定为 Antigravity、Codex++、VSCode Claude Code 中用户当天输入的任务命令、追问、修改要求、验收反馈和继续执行指令；同时必须补扫独立 Codex 当天会话，独立 Codex 不得被三入口预采集遗漏。
- **git 只做辅助校验**：git commit、git status、文件变更和自动产物只能用于补证据、反查结果或校验主线，不再主导日报条目。
- **脚本做采集，Agent做归并**：脚本负责稳定抽取三入口输入流和辅助证据；Agent 负责合并同义任务、过滤闲聊/系统注入/自动噪声，再写日报。
- **日报是业务翻译层**：三入口输入流和本地证据只用于判断事实，不能原样搬进日报。Agent 必须把脚本名、字段名、故障码、文件名、英文缩写、流水线术语和内部链路名翻译成领导能看懂的工作结果、影响和下一步。
- **角色定位**：Agent 是日报编写者和工作整理者，不是当天工作的技术执行者，也不是 cron 执行回执机器人。它只能整理“用户今天指挥和推进了哪些工作”，不得把自己运行脚本、检查文件、遇到报错、保存证据的过程写成日报内容。
- **第一性原理规划**：正式写日报正文前，必须先在内存中完成工作版图规划：今天有哪些工作主线；每条主线实际做了什么；产出或影响是什么；明天还要跟进什么。最终飞书只输出整理后的日报，不输出规划过程。
- **事项价值补充**：不要单独写 `说明：...` 行。把工作价值直接补在对应事项后面，用一句完整中文说明这个事项解决了什么问题、减少了什么风险、发现了什么关键问题或带来什么交付价值；禁止只写 10～20 字短句。
- **日报评分质量硬规则**：日报必须按“给大模型打分”的质量来写。每条尽量写成“完成/验证/排查了什么 + 具体对象/现象 + 结果价值/影响”的完整句；单条建议 45～90 个中文字符，复杂事项可以更长，但必须清楚、有信息量、可评分。用户当天明确补充的真实业务事项优先级最高，若自动采集摘要或 Cron 结果过短、漏主线，必须以用户补充信息和三入口输入流为准重写，不得交付短版。
- **真实业务补充优先**：写日报前必须重点检查是否遗漏用户当天补充的真实业务事项，尤其是涛哥交代的小红书“快穿乙女”竞品分析、生产环境 APP 测试缺陷、Jira 责任人与优先级、GPT5.6 反爬安全机制配置、爬虫平台治理、Codex 自动化治理等主线。Jira 类缺陷必须保留责任人和优先级，并写清实际现象、预期结果和影响。
- **全量盘点但合并表达**：三入口用户输入中出现过的人工主导工作都要纳入候选，不得只挑技术提交；同一方向反复追问、排查、修复和验收要合并成一条能读懂的工作主线。
- **职责分离**：Skill 负责**如何生成内容**（原子能力），Workflow 负责**何时触发及流程编排**（业务流）。
- **合并规则 (项目级高维铁律)**：
    - **【大标题真实项目级】制约**：日报的最高一层板块（大标题）**必须并且只能**是顶层的“核心大项目”或“重要评测类”名称！严禁使用细小需求、局部小功能、碎小的模块名来充当大标题，从而导致整个周报版面碎裂得没法看。
       - ✅ **极其正确的大标题**：`【Codex 自动化治理】`、`【竞品平台爬虫能力建设】`、`【PatchX 智测平台后端】`、`【AI 测试用例中台】`、`【APP 软硬件交互测试】`。
       - ⚠️ **项目命名永久偏好**：日报标题或项目名中凡是出现 `【OpenClaw 自动化治理】`，一律改写为 `【Codex 自动化治理】`；不要再把自动化治理类日报写成 OpenClaw 口径。
       - ⚠️ **Codex 统一归类**：日报正文禁止出现 `【Codex 基础建设】`。凡是 Codex、Codex++、OpenClaw、LangGraph、hook、cron、Skill、提示词知识库、质量门禁、账号隔离、配置切换、运行环境、命令入口、Dashboard、认证代理等相关工作，全部统一归入 `【Codex 自动化治理】`。
       - ⚠️ **爬虫治理表达边界**：竞品、DSP、TopHub、Walmart、闲鱼、采集 worker、数据源统一、登录态、收割、调度等内容统一归入 `【竞品平台爬虫能力建设】`，日报表达要写成“梳理采集架构缺口”“处理平台登录协同”“统一采集调度”，不要写内部代号或技术链路。
       - ❌ **绝对错误的大标题**（降级下沉到了功能/需求卡片）：~~`【飞书文档自动化工具】`~~、~~`【内部工具与日报优化】`~~、~~`【日志处理框架】`~~。遇到这类局部业务的零碎修改，必须要求大模型拔高视野视线，找到它们的“老子（所属的宏观物理系统大项目）”，然后挂靠进去作为附庸子点输出！
    - **干了的活都要罗列，但是不需要技术细节，罗列出来，然后分类汇总**：这是极其重要的铁律！必须确保一天当中横跨多个项目的所有平行任务点都不会被遗漏，全面地网罗在一个个大骨架下。
    - **对于开发任务**：将全部离散的代码提交和脚本调试折叠归类到上述顶级大项目标签下。在项目级标签下，用业务线索串联所有底层提交，绝对禁止碎块化动作的新建任务罗列！
    - **对于测试任务**：直接剥离并分类聚合为【语音测试】与【固件测试】两大独立最高阵营。其余所有的环境微调、日志补充动作均纳入其子分类。
    - **领导视角 (Manager Friendly) 🆕**: 严禁堆砌技术黑话（如“异步自旋断言”、“时序边界编排”）。
    - **口语化表达**: 表达要直观、通俗，让非技术的领导一眼能看懂这堆改动到底“做出了什么业务产品”。
    - **技术证据禁止直出**：最终日报正文和待处理事项禁止出现 `CRON_HARD_FAIL`、`FAIL_`、`receipt`、`sidecar/侧车`、`.json`、`PID`、`stdout`、`stderr`、`schema`、`manifest`、`hook-state`、`OpenCLI command`、具体文件路径、章节号、错误码或英文堆栈。证据表可保留原文，日报必须翻译。
    - **固定翻译示例**：`Reference 侧车缺失 skill_governance_receipt.json` -> `提示词知识库检查结果还需补齐`；`LangGraph CLI 接口开发` -> `补齐自动化流程命令入口`；`Walmart/闲鱼 worker 协同` -> `处理多个平台采集协同`；`Interrupt 决策引擎 L1 §345` -> `完善任务中断处理规则`。
- **约束指标**：
    - **禁止短清单**：每项工作描述不得退化为 10～20 字的动作短句，必须写出具体对象/现象和价值影响。
    - **单条长度建议**：每项工作描述建议 45～90 个中文字符；复杂事项可以更长，但要保持清楚、可读、可评分。
    - 每个工作大项应代表一个完整的交付物、测试发现、排查结果或业务成果。
    - 工作大项数量建议控制在 3-6 个项目级板块；每个板块下合并表达，不要碎片化堆技术动作。
    - **质量胜过数量**: 宁可合并为一个有价值的大项，也不要列出 10 个琐碎的技术动作。
    - **输出前自检**：如果任何一级项目只有 1～2 条，或多数条目短于 35 字，视为质量不合格，必须重新归并和扩写。
    - **Fail-fast (快速失败)**: 如果既没有三入口用户输入事实，也没有用户明确补充的对话语义事实，严禁伪造日报内容，应直接报错。
    - **示例不是事实**: 本文中的 `【OpenClaw 基础设施】`、`【PatchX 智测平台后端】`、`【AI 测试用例中台】`、`【终端语音质量评测】` 只作为标题分类示例，绝不能因为示例存在、历史日报存在、资产注册表存在，就写入当日日报；`【Codex 基础建设】` 不是允许标题，必须并入 `【Codex 自动化治理】`。
    - **证据命中才准上报**: 任一项目标题必须被当天有效证据命中后才能进入正文。有效证据首先来自今日三入口用户输入流；今日 git commit、今日 git status 变更、今日产物文件正文只能作为辅助校验。仅有目录名、缓存文件、历史备份、`pipeline_state`、`sessions`、`hook-state`、`.gemini/code_tracker` 文件名，不得生成日报条目。
    - **定时任务产物默认过滤**: 由 OpenClaw cron/isolated 定时任务自动生成、搬运或同步的内容，默认不得写入“个人今日工作日报”。例如自动日志日报、自动监控交付、自动趋势看板同步等，只能进入系统运行记录或单独监控日报。除非用户明确要求“把定时任务结果也计入今天工作”，否则必须从工作日报正文剔除。
    - **夜间任务与日报规范治理过滤**: 夜间定时任务、心跳巡检、知识蒸馏/回流自动执行结果、日报格式纠偏、日报 Skill 规则固化等“系统治理/流程规范”动作，默认不得写入个人每日工作日报；它们只进入系统运行记录、错题本、memory 或 Skill 资产变更记录。只有用户明确要求把这类治理动作计入日报时，才允许作为独立条目出现。
    - **人工工作优先**: 日报只写当天人工主导的设计、排查、开发、评审、修复、决策和交付动作；后台定时任务的自动产物只能作为系统状态背景，不能包装成人工工作量。
    - **待处理事项翻译规则**: 待处理事项只写次日要推进的业务动作，不写内部失败链路、故障码、文件名、字段名和英文缩写；每条建议控制在 22 字以内。无法翻译成领导能懂的一句话时，说明该项不适合进入日报正文。
    - **事项补充质量**: 事项后面的补充必须回答“为什么这件事值得汇报”。禁止写“提升效率、优化体验、加强治理”这类空话；要写成“提交三项体验Bug，提前暴露影响体验的问题”“清理无效定时任务，减少夜间误报”“处理平台登录协同，减少采集失败”。
    - **用户补充事项覆盖**: 如果用户当天补充了具体业务工作或测试缺陷，必须优先纳入日报，并保留关键业务信息、责任人和优先级；不得被自动摘要、git 记录或 cron 回执稀释。
    - **APP/Jira 缺陷写法**: APP 生产包测试、软硬件联调、Jira 缺陷、责任人和优先级统一归入 `【生产环境 APP 测试与缺陷流转】`；每条缺陷必须写清“实际现象 + 预期结果/影响 + 责任人优先级”。
    - **APP/Jira 覆盖矩阵硬门**：当用户当天给出 APP/Jira 缺陷清单时，正式日报前必须形成 `coverage_matrix` / “APP/Jira 缺陷覆盖矩阵”，逐项标记“用户补充事实、责任人/优先级、采纳/合并/剔除、归并到日报哪一条”；日报正文允许合并表达，但矩阵不得漏项。
    - **条目级证据表**: 写最终日报前必须先形成“候选条目 -> 证据来源 -> 是否采纳/剔除原因”的审计表。无证据或证据只有噪声文件的候选条目必须剔除。
    - **文件名日期校验铁律**: 如果证据文件名包含日期（如 `2026-06-23.md`、`报告-2026-06-23.txt`），必须校验该日期是否与日报日期（今天）匹配。**不匹配时默认剔除**，除非：
      - 用户明确说明“今天整理/上传昨天的测试报告/工作记录”
      - 文件正文开头明确标注“生成日期：今天”（而非文件名日期）
      - git commit 时间戳是今天且 commit message 说明“整理历史文档”
      - 否则，文件名日期为昨天的证据应视为“历史补充”而非“当日工作”。
    - **知识回流必须走 M4 流程**: 当日报生成过程中发现新的经验教训（如定时任务故障、证据链断裂、流程改进点）需要沉淀时，**禁止直接写入错题本**，必须按 M4_知识回流分析 的标准流程执行：(1) 先入队 `governance/experience_queue.md`；(2) 由 M4 状态机分诊路由到对应 Skill 错题本；(3) 闭环验证后清空队列条目。跳过 experience_queue 直接写错题本是流程违规。
