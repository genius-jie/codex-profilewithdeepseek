# 架构决策 SOP 准则 (Architecture Decision Protocol)

> **核心定律**: 先收敛方案，再展开实施。方向错了，执行力越强，离目标越远。

---

## 🏛️ 七大决策铁律

### 铁律 1：先定义目标能力，再选承载层

**What（规则）**:
在做任何技术选型前，必须先回答：**"我要给系统增加什么能力？"**，然后再问 **"谁应该真正拥有这个能力？"**，最后才是 **"通过什么技术手段实现？"**。

**Why（根因）**:
如果跳过能力归属的判定，直接从技术手段入手，极易选择一条"看似合理但本质绕路"的架构路径。一旦走上这条路，后续所有努力都是在修补次优架构的局部故障。

**Evidence（证据）**:
OpenClaw 桌面自动化案例 — 目标是"让龙虾拥有桌面控制能力"，但实际走了 `OpenClaw → ACPX → 外部 ACP Agent → Darbot` 的四层链路，导致长时间在排查中间层故障。正确路径是直接在 OpenClaw 工具层集成 Darbot。

**可操作级别**: 🔴 铁律

**决策检查清单**:
```
□ 目标能力是什么？（一句话描述）
□ 这个能力的真正宿主是谁？（哪个系统/层应该拥有它）
□ 有没有不经过额外中间层就能实现的方案？
```

---

### 铁律 2：先找原生能力边界，再决定要不要扩展

**What（规则）**:
对任何系统做改动前，必须先完整查阅其**原生文档、插件机制、配置能力**，确认系统已有的能力边界。只有在证明原生能力确实不足时，才允许引入扩展。

**Why（根因）**:
很多系统已内建了丰富的扩展点（如插件、工具注册、配置路由），直接使用原生机制的方案通常更稳定、更易维护。如果不先调研就引入外部桥接层，会造成两层体系并行、维护负担加倍。

**Evidence（证据）**:
OpenClaw 原生支持 MCP 工具注册（通过 `openclaw.json` 的 `mcpServers` 配置），可直接将 Darbot 注册为 OpenClaw 工具。但早期未充分调研就选择了 ACPX 外部代理方案。

**可操作级别**: 🔴 铁律

**决策检查清单**:
```
□ 是否已阅读目标系统的官方文档？
□ 目标系统原生支持哪些扩展机制？（插件/工具/配置/API）
□ 原生机制是否已能满足需求？（是 → 用原生；否 → 记录不足点再扩展）
```

### 铁律 3：渠道层和工具层必须解耦

**What（规则）**:
消息渠道（如飞书、Slack、Web）只负责消息的输入/输出，工具能力（如桌面自动化、文件操作、API 调用）必须在独立的工具层注册。严禁因为用户入口在某个渠道，就把工具能力塞进该渠道的插件体系。

**Why（根因）**:
渠道和工具如果耦合，会导致：① 同一工具需要在每个渠道重复集成；② 渠道故障会连锁影响工具可用性；③ 架构层次混乱，难以独立升级。

**Evidence（证据）**:
桌面自动化能力与飞书消息渠道无关。但因为用户通过飞书下达指令，早期方案试图通过飞书插件体系（ACPX）来桥接桌面工具，导致飞书 session 管理和桌面控制逻辑纠缠在一起。

**可操作级别**: 🔴 铁律

**决策检查清单**:
```
□ 新增能力是"渠道类"还是"工具类"？
□ 该能力是否依赖某个特定渠道才能工作？（不应该）
□ 换一个渠道入口，该能力是否还能正常运作？（必须是）
```

### 铁律 4：新增中间层必须先证明必要性

**What（规则）**:
每新增一层代理、一层 session、一层协议适配，都必须先回答：**"没有这一层，真的不行吗？"**。如果无法给出有力的证明，该中间层不应被引入。

**Why（根因）**:
每多一层中间件都会放大故障面：多一层认证、多一层超时、多一层日志盲区、多一层版本兼容问题。系统复杂度不是线性增长，而是组合爆炸。

**Evidence（证据）**:
`OpenClaw → ACPX → ACP Agent → Darbot` 链路中，ACPX 和 ACP Agent 两层中间件引入了 session 管理、协议适配等额外复杂度，而实际上 OpenClaw 可以直接通过 MCP 协议调用 Darbot，省去两层中间件。

**可操作级别**: 🔴 铁律

**决策检查清单**:
```
□ 列出当前方案中所有中间层
□ 逐层回答：去掉这一层，系统能否工作？
□ 每保留一层，必须记录其不可替代的理由
□ 超过 3 层中间件的方案需要强制架构评审
```

### 铁律 4.1：Canary 可行性不等于生产采纳

**Canary / POC PASS 只证明技术可行**，不证明该机制已经必要、应成为长期生产架构，或获得后续实施授权。拟把一个机制放入正式 Runtime、正式入口或长期资产前，P2 必须进行一次**生产采纳双轨复审**；它是既有 P2 的设计判断，不新建 Gate、Engine、Registry 或状态机。

```
Production Adoption = 7+1 责任审计 PASS + 最小充分性审计 PASS
```

**轨道 A：7+1 / 原生责任审计**

```
□ 要守住的 observable invariant 是什么？
□ 主 Plane、唯一 Owner、正文 SSOT、发布政策 SSOT、真实 consumer 与正式入口分别是什么？
□ 发布资格、物理投影、Host Catalog、当前选择、正文消费是否被明确分开？
□ 谁是唯一的投影 Writer？Host 私有实验层不能仅因 Canary 可调用而充当正式 Owner。
□ Runtime 是否会改写政策，或让可重建投影变成第二状态源？
```

**轨道 B：最小充分性审计**

```
□ 现有最小方案为什么不够？是否有重复、真实的失败证据？
□ 新 Worker、持久 state、journal、transaction、第二 Guard、Host 私有 patch 各有什么不可替代理由？
□ 派生投影能否从 canonical SSOT + policy + 物理事实直接重建？
□ 局部能力故障会不会被升级为整个 Host 的启动门？
□ 是否可在既有正式入口调用一个无状态、幂等的收敛动作解决？
□ 该资产的退役条件是什么？
```

结论只能是 `adopt`、`simplify` 或 `observation_only`。任一轨答不清时停止生产化，保留 Canary 作为 Observation 或收缩为更小解；投入、测试数量和已写代码都不是保留理由。Follow-up、Observation、候选下一步或评审建议也不构成新的 Change Intent 或实施授权。

### 铁律 5：先出架构文档，再做实现

**What（规则）**:
对于任何**高风险改动**（定义：涉及跨系统集成、新增依赖层、改变数据流向），必须先输出架构决策文档，文档包含：**目标、现状、证据、候选方案、风险评估、推荐方案**。经确认后再进入实施。

**Why（根因）**:
没有文档约束的实施会陷入"边修边找方向"的模式 — 看起来一直在努力解决问题，但实际上是在不断修补一条本不该成为主路径的链路。方案选型越晚收敛，沉没成本越高。

**Evidence（证据）**:
桌面自动化集成过程中，未在方案选型阶段充分评估就进入实施，导致在 ACPX 链路上投入了大量调试和修补时间，最终仍需回到正确方案重新开始。

**可操作级别**: 🔴 铁律

**架构决策文档模板**:
```markdown
# [能力名称] 架构决策记录 (ADR)

## 1. 目标
我们要给系统增加什么能力？

## 2. 现状
当前系统在这个方面的能力边界是什么？

## 3. 候选方案
| 方案 | 链路 | 中间层数 | 原生支持 | 风险 |
|:---|:---|:---|:---|:---|

## 4. 推荐方案及理由

## 5. 风险与缓解措施

## 6. 验收标准
```

### 铁律 6：优先单一事实来源和最短闭环

**What（规则）**:
系统设计必须追求：① 链路最短；② 职责清晰（每层只做一件事）；③ 升级不易被覆盖（配置和代码分离）；④ 日志和责任边界清楚（出问题能 10 秒内定位到是哪一层的故障）。

**Why（根因）**:
长链路意味着更多的故障点、更长的排查时间、更模糊的责任归属。短闭环设计让系统更鲁棒，也让调试更高效。

**Evidence（证据）**:
四层链路 (`OpenClaw → ACPX → ACP Agent → Darbot`) 中，当 Darbot 工具调用失败时，需要逐层排查是 OpenClaw 配置问题、ACPX session 问题、ACP 协议问题还是 Darbot 本身的问题。而两层链路 (`OpenClaw → Darbot`) 的故障域只有两个，定位速度提升数倍。

**可操作级别**: 🔴 铁律

**设计检查清单**:
```
□ 画出完整调用链路图，标注每一层的职责
□ 链路总层数是否 ≤ 3？（超过则需要强制简化论证）
□ 每一层是否只做一件事？（不允许混合渠道和工具职责）
□ 出故障时，能否在 10 秒内定位到是哪一层的问题？
□ 配置升级后，是否会被其他层的更新覆盖？
```

### 铁律 7：绝对禁止 --ignore-scripts 安装依赖

**What（规则）**:
执行 `npm install` 时，**绝对禁止**使用 `--ignore-scripts` 标志。该标志会跳过所有 `postinstall` 脚本，导致依赖于编译/安装后置脚本的包（如 Python 原生模块、C++ addon）静默缺失，但 `npm install` 本身不会报错。

**Why（根因）**:
很多 npm 包的 `postinstall` 脚本负责关键的安装步骤：编译原生模块、下载平台特定二进制文件、安装 Python 依赖等。`--ignore-scripts` 会让这些步骤全部被跳过，包的目录结构看似完整但功能残缺。错误会延迟到运行时才暴露，且错误信息通常指向"模块找不到"或"函数未定义"，**极难定位到是安装阶段的问题**。

**Evidence（证据）**:
OpenClaw 安装过程中使用 `npm install --ignore-scripts` 跳过了 Python 依赖的安装步骤，导致后续运行时出现依赖缺失。由于错误表现为运行时异常而非安装时报错，排查过程浪费了大量时间。

**可操作级别**: 🔴 铁律

**决策检查清单**:
```
□ npm install 命令中是否包含 --ignore-scripts？（绝对禁止）
□ 如果安装过程中 postinstall 报错，应修复报错原因，而非绕过
□ 如果确实需要跳过某些脚本，必须手动逐一执行被跳过的关键 postinstall
```

## 🚨 红旗信号 — 架构决策质量自检

当你在做技术选型时，如果出现以下想法，**立即停下来，回到铁律 1**：

| 红旗信号 | 说明 |
|:---|:---|
| "这个方案看起来更酷/更先进" | 技术选型不追求先进，追求最短路径 |
| "先把它跑起来再说" | 跑起来不等于方向正确 |
| "加一层代理应该能解决" | 加中间层是最后手段，不是第一反应 |
| "这个方案只是暂时的" | 临时方案往往变成永久方案 |
| "我们已经在这个方案上投入很多了" | 沉没成本不是继续走错路的理由 |
| "先做出来，文档以后补" | 高风险改动没有文档 = 没有方向锚点 |
