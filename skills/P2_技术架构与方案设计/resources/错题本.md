## 域专属错题本

### 坑位 1：Tech Spec 缺少多 Agent 管线专用模板

*   **【反例】**：
    面对"多角色 DAG 协作流"（如爬虫+审计+报告生成管线）需求时，P2 仍使用标准单体应用模板（DB Schema、前后端握手 JSON）去输出 Tech Spec。
*   **【后果】**：
    P4 拿到的图纸"格式不对口"——缺少 Agent 角色清单、拓扑模式推荐、Tool 函数签名、质量门设计等关键信息，P4 需要脑补翻译，增加了出错概率。
*   **【正例（SOP）】**：
    在 PHASE_5_TECH_SPEC_MINTING 中，经 7D 对冲判定为"多 Agent DAG 协作流"的需求，必须切换到 Pipeline Variant 替代骨架（已内置于 P2 SKILL.md 第 127-158 行）。

### 坑位 2：POC 验证不充分导致架构图纸变幽灵连线

*   **【反例】**：
    P2 在 Tech Spec 中画了一条 A→B 的交互连线，但这条连线没有经过物理 POC 验证（如 curl/requests 实际调用），纯粹是"我觉得应该能通"。
*   **【后果】**：
    下游 S10 照着图纸写代码时发现 A 根本调不通 B（比如 API 需要额外的认证步骤、或者返回格式跟画的不一样），被迫返工。
*   **【正例（SOP）】**：
    P2 SKILL.md 第 100 行"图纸诚实性原则"明确要求：上图中所有的交互连接线都在本地隔离的 POC 沙盒中经由硬核代码抓到了确切的出入栈 JSON。

### 坑位 3：技术通道盲视——只管"怎么拿"却不管"拿什么"导致下游养料断供

*   **【反例】**：
    Marketing Video Crawler 项目中，P2 在做三个营销网站的提取架构时，全部精力投入在"API vs SSR vs DOM 哪条技术通道能打通"（连通性验证），POC 脚本跑通了就宣布 PASS。结果实际提取器写完后发现：梅花网明明 API 返回了 `favors`（点赞）和 `comments`（评论数），提取器却只取了 `views`；SocialBeta 的 `metrics` 字段直接留空；三个站点均未提取封面图（cover）、视频时长（duration）、操盘手/行业标签（agency/category）、用户真实评论等关键维度。
*   **【后果】**：
    下游 LLM 清洗层（Mod-202）在执行"业务三层解剖"（感官事实层→穿透逻辑层→实战战报层）时，因为缺乏互动数据和真实舆论，只能被品牌方的 PR 软文洗脑，产出的 `popularity_reason` 和 `user_emotions` 沦为假大空废话，彻底违背 PRD "禁止空洞总结，必须具体指导"的铁律。
*   **【病因诊断】**：
    P2 的 POC 验证只打到了"技术通道层"（能不能连通、能不能拿到 HTML/JSON），完全没有向上反推"业务消费层到底需要哪些维度的事实养料才能还原真相"。本质是 P2 在做架构选型时，把"需求对齐"窄化为"功能跑通"，而忽略了"交付质量对齐"。
*   **【正例（SOP）】**：
    P2 在 POC 验证阶段，必须先从 P1 PRD 的输出 Schema 反向推演出"下游分析/处理层需要的全部事实维度清单"，然后逐维度验证数据源是否能供给。已注入 P2 SKILL.md 的 PHASE_2 状态机中，作为"需求养料逆推铁律"永久生效。

## [2026-04-17] 提示词层纪律无法物理阻止同上下文形式化分步
- **症状**：P2 的 Slice 分片铸造协议要求"必须分步写、每步验证"，但同一个上下文里模型可以先在脑内预构思全部 5 Slice 再假装逐片落盘。三重防线（写盘回读 + 自反决策卡 + 跨脑审计建议）停留在提示词层，无法制造真正的物理中断。
- **病因**：提示词约束的本质是"软劝告"，模型在同一上下文中拥有完整的前后文记忆，可以在形式上分步但实质上一把过。
- **解法（四刀）**：
  1. 防线零：注入 `pipeline-state.yaml` 外部状态机，每 Slice 的 status/human_approval_token 必须由外部文件裁决
  2. 防线二增强：人类批准后必须先回写状态再动笔
  3. 防线三升级：Slice 3 和 Reduce 的 P2.6 微审计从"建议"升级为"不可跳过的制度性卡口"
  4. 自动模式边界锁定：分片阶段门禁任何模式不可绕过
- **通用范式**：四层门禁可从 P2 抽象为参数化的 `p-level-gate-protocol.md`（Gate-0 状态机 / Gate-1 写盘回读 / Gate-2 人类签章 / Gate-3 跨脑审计），落入 M2 出站检查

## [2026-04-12] 模型偷懒的数学根因：覆盖率换深度
- **症状**：面对大任务时模型本能用覆盖率换深度——急着填满所有章节而不是每章做扎实。
- **病因**：提示词约束管的是"必须做什么"，但管不了"做到什么深度"。
- **解法（物理分治引擎）**：把大任务拆成极小的微验证片（Micro-POC），每片完成后必须立刻输出结构化证据卡片。最终 Tech Spec 从卡片拼装（Assembly）而不是从脑子里回忆（Recollection）。
- **原理**：等同于 S27 的强制逐 50 行阅读——任务小到"偷懒和做好是同一件事"。已植入 P2 PHASE_2。

## [2026-04-16] P系管线全链路 5W1H 数据契约标准化
- **症状**：P3 执行层问题的根因不是模型能力不足，而是信息在 P2→P2.5→P3 传递中逐层蒸发。P2 写的"用 BeautifulSoup"到了 S 兵团手上变成正则，P2 验证的 POC 脚本从未传给执行者。
- **病因**：P 级节点间的交付物是散文描述而非结构化契约，经过每个人的"大脑理解"后信号衰减。
- **解法**：
  1. schema-registry 的 §1~§6 全部统一为 WHO/WHY/WHAT/HOW/WHERE/RULES/VERIFY 结构
  2. §2 新增 `how.implementation_constraints` 和 `how.proven_approach` 填补 P2→P2.5 载体空白
  3. P3 新增 MICRO_DESIGN 状态强制铸造 5W1H 蓝图供 S 兵团使用
  4. P3 验收新增四维 grep 核验替代 LLM 理解型验收
- **铁律**：交付物的数据契约必须是结构化 JSON 的机械传递；验收必须是确定性的 grep 命令。
