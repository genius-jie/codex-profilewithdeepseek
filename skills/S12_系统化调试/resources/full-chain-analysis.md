# 全链路分析排查 (Full-Chain Analysis)

## Overview

调试多组件系统时，只盯着报错点修复是最常见的认知陷阱。错误的表现点往往不是根因所在层，更不是唯一受影响的层。

**核心原则:** 面对多组件系统故障，必须拉通整条链路做端到端排查，禁止以点概面——单点症状可能掩盖多点病灶。

## 与现有技术的区别

| 技术 | 视角 | 适用场景 |
|:---|:---|:---|
| **Root Cause Tracing** | 纵向：沿单条调用链向上追溯 | 单一调用链上的数据传递错误 |
| **Defense-in-Depth** | 纵向：修复后在各层加守卫 | 修复后的防御加固 |
| **全链路分析（本文）** | **横向：拉通所有组件做端到端扫描** | **多组件系统故障、症状与根因不在同一组件** |

```
Root Cause Tracing = 沿着一根绳子往上爬
全链路分析 = 先看清整张网，再决定爬哪根绳

Defense-in-Depth = 修完之后加锁
全链路分析 = 修之前先画地图
```

## When to Use

**必须使用全链路分析的信号：**
- 系统涉及 3 个及以上组件协作（如：前端 → API → 数据库 → 消息队列）
- 报错信息模糊或只有最终症状（如：Timeout、Connection Refused、数据不一致）
- 同一个修复在不同环境表现不同
- 修了 A 组件的 bug，B 组件又冒出新问题
- 多个组件同时出现"看起来无关"的异常

**不要使用的场景：**
- 错误明确指向单个文件的单行代码
- 纯算法逻辑错误（不涉及组件交互）

## 全链路分析五步法

### 第一步：画链路图 (Map the Chain)

**在动手排查之前，先画出完整的组件交互链路。**

```
问题表现 → 组件 A → 组件 B → 组件 C → 组件 D
                ↑                        ↑
              你以为的问题            真正的根因
```

**动作：**
1. 列出从用户输入到最终输出经过的所有组件
2. 标注每个组件之间的交互方式（HTTP、RPC、消息队列、文件、环境变量等）
3. 标注每个交互点的数据格式和协议

**产出：** 一张覆盖完整链路的交互图，哪怕只是文字版。

### 第二步：全链路健康扫描 (Health Sweep)

**不要只检查报错的组件，逐一检查链路上的每个节点。**

```
对于链路上的每个组件：
  1. 该组件是否存活？（进程、端口、服务状态）
  2. 该组件的输入是否正常？（上游给了什么）
  3. 该组件的输出是否正常？（下游收到了什么）
  4. 该组件的配置/版本是否符合预期？
```

**关键：不能跳过"看起来没问题"的组件。**
- "看起来没问题"≠"确认没问题"
- 必须有证据（日志、探针、手动请求）证明该节点健康

### 第三步：缩小断裂区间 (Isolate the Break)

**通过二分法或边界探针，定位链路断裂的精确位置。**

```
组件A ──[正常]──→ 组件B ──[异常]──→ 组件C
                          ↑
                     断裂点在这里
```

**方法：**
- 在每个组件边界注入探针（参见 SKILL.md Phase 1.4 的多层诊断法）
- 从两端向中间逼近：确认链路头部正常、尾部异常，逐步缩小
- 记录每个边界的实际数据，不要凭假设跳过

### 第四步：关联分析 (Correlation Analysis)

**找到断裂点后，不要立即修复，先检查是否存在关联问题。**

```
问自己：
  1. 这个断裂点是否影响了链路上的其他组件？
  2. 是否有多个断裂点？（多点故障）
  3. 这些断裂点是否有共同的上游根因？
```

**以点概面的典型错误：**

| 错误 | 后果 |
|:---|:---|
| 只修了 A 组件的 bug，没检查 B 也受到影响 | B 在下一轮测试爆炸 |
| 看到 Timeout 就调大超时时间 | 掩盖了底层组件崩溃的真相 |
| 数据库查询慢就加索引 | 没发现上游在循环里发了 1000 次查询 |
| API 报 500 就修 API 代码 | 没发现是下游队列堆积导致的级联失败 |

### 第五步：系统性修复与验证 (Systemic Fix & Verify)

**修复必须覆盖所有受影响的组件，验证必须走完全链路。**

1. **修复作用域评估**：一个根因可能需要在多个组件落地修复
2. **全链路回归测试**：不能只测修改的组件，要从链路头跑到尾
3. **涟漪效应检查**：修复后检查链路上的其他组件是否出现新的异常

## 防范"以点概面"的思维检查清单

在得出结论之前，逐条检查：

- [ ] 我是否画出了完整的组件链路图？
- [ ] 我是否检查了所有组件，而不仅仅是报错的那个？
- [ ] 我是否有证据证明"没问题"的组件确实没问题？
- [ ] 我的修复方案是否考虑了对链路其他组件的影响？
- [ ] 我的验证是否走完了端到端全链路？

**如果任何一项答"否"，你的结论是不完整的，继续排查。**

## 实战案例

### 案例：MCP Bridge 启动超时

**症状：** Gateway 报 "MCP Server 启动超时"

**以点概面的做法（错误）：**
→ 调大 Timeout → 仍然超时 → 检查网络 → 网络正常 → 困惑

**全链路分析的做法（正确）：**

```
链路图：Gateway → Node Bridge → Python MCP Server → uv 环境 → 系统 Python
```

1. **健康扫描**：
   - Gateway：存活 ✓，发出了启动命令 ✓
   - Node Bridge：存活 ✓，调用了 child_process ✓
   - Python MCP Server：**100ms 内崩溃退出** ✗
   - uv 环境：未安装 ✗
   - 系统 Python：缺少 markdownify 模块 ✗

2. **断裂区间**：Node Bridge → Python MCP Server（子进程瞬间崩溃，但包装层没捕获 stderr）

3. **关联分析**：两个独立根因（uv 缺失 + 模块缺失），任一修复都不够

4. **系统性修复**：安装 uv + 安装 markdownify + 加强 Bridge 的 stderr 捕获

> 这个案例同时出现在错题本陷阱 1 (Error Masking)，但错题本只记录了"跳过包装层直接运行"这一个技巧。全链路分析提供的是完整的方法论框架。

## 与 SKILL.md 主流程的关系

全链路分析是 **Phase 1（Root Cause Investigation）** 的一个增强扩展：

```
Phase 1 标准流程:
  1. 读错误信息        ← 单点
  2. 复现问题          ← 单点
  3. 检查近期变更       ← 单点
  4. 多组件诊断        ← 已有多层探针，但缺少全局视角
  5. 追溯数据流         ← 纵向追溯

全链路分析补充:
  0. 画链路图          ← 先建立全局视角（新增）
  4+. 全链路健康扫描    ← 横向扫描每个节点（增强）
  4+. 关联分析         ← 检查多点故障和涟漪效应（新增）
```

**使用时机：** 当 Phase 1.4 的多组件诊断完成后，如果发现系统涉及 3 个及以上组件，应切换到全链路分析模式。

## Real-World Impact

- 全链路分析 vs 单点排查：30 分钟定位 vs 数小时在错误组件上打转
- 修复完整率：95%（覆盖关联组件） vs 60%（只修单点，下轮又炸）
- 认知负载：前置画图投资 5 分钟，节省后续反复折腾的时间
