## 陷阱 1: Error Masking (错误掩盖与"假"超时)

**What（规则）**: 
当调试带有包装层（Wrapper/Bridge，如 Node 调 Python、Gateway 调 Agent）的全链路系统时，若顶层持续报 `Timeout` 或 `Connection Refused`，**必须跳过包装层，直接去底层沙盒中运行真正的可执行文件**。

**Why（为什么）**: 
包装层通常会通过 `child_process` 唤起子进程。如果子进程因为严重的底层错误（如 `ModuleNotFoundError`）在 100 毫秒内瞬间崩溃退出了，缺乏健壮性的包装层不仅抓不到 stderr，还可能傻傻地挂起一个 15 秒的 Timer，最终抛出 `Timeout`。这会将排障思路完全带偏（去查网络或调大 Timeout）。直接执行底层命令，能让隐蔽的崩溃瞬间无所遁形。

**Evidence（证据）**: 
[MCP Bridge 直连血泪史]：报错 "MCP Server 启动超时"。排查数小时无果。直到裸写启动命令 `node darbot-mcp.js` 才发现真实输出是因为系统缺失 uv 环境而回退，且系统 Python 缺失 `markdownify` 导致瞬间崩溃退出。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 2: Zombie Process (僵尸进程防线)

**What（规则）**: 
重启常驻后台服务或计划任务（如 Gateway）以应用新版本/新插件时，**严禁只依赖 `service stop` 和 `service start`**。必须检查并强杀目标端口占用。

**Why（为什么）**: 
包含错误代码的旧进程可能会卡死并脱离了服务管理器的控制，变成僵尸进程霸占着核心端口（如 18789）。当你执行 `start` 时，新进程发现端口被占直接静默失败，而此时响应你请求的，依然是那个缺少最新代码/插件的旧僵尸进程！让你误以为"新代码没生效"并反复自我怀疑。

**Evidence（证据）**: 
[端到端联调血泪史]：不断修补 MCP Bridge 并重启 OpenClaw Gateway，但 Agent 始终说找不到工具。最后用 `netstat -ano | findstr 18789` 发现初始挂掉的那个 PID 32960 一直在苟活，拦截了所有的飞书请求，而带有新工具注册列表的新 Gateway 从未真正启动过。必须使用 `schtasks /End` 配合 `taskkill /F /PID` 才能彻底清空战场。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 3: The Iron Rule Trap (提示词禁令反模式)

**What（规则）**: 
在 Agent 的 SOUL/System Prompt 中编写行为约束时，**禁止使用绝对禁令（"严禁 X"）来限制有更优替代方案的操作**。应使用**优先级分层**（"优先 A，不可用时降级 B"）。绝对铁律只用于客观上永远不该做的事。

**Why（为什么）**: 
Agent 的可用工具集是**动态的**——工具注册可能因缓存、网络、编译等原因失败。如果提示词用"严禁 exec"堵死了降级通路，而 desktop-* 工具又因故未注册，Agent 就会陷入"想做做不了，能做不让做"的死锁，最终只回复"收到"但什么都不执行。**规则不能比能力更激进。**

**Evidence（证据）**: 
[SOUL.md 铁律导致龙虾瘫痪]：SOUL.md 写了"严禁用 exec/shell 操作 GUI，必须走 desktop-* 工具"。当 jiti 缓存导致 desktop-* 工具注册失败后，Agent 无法降级到 exec，Session 日志显示 Agent 只回复了"收到，正在处理"后不再有任何 tool_use 调用。修改为"优先级分层 + 自动降级"后恢复正常。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 4: Environment State Blindness (环境态盲区)

**What（规则）**: 
当调试"配置已正确但行为不生效"的问题时，**必须先排查环境态（残留进程、缓存、端口占用、旧 session），再怀疑代码逻辑**。执行以下三步环境态体检后才允许进入代码调试：

1. **进程体检**：`Get-NetTCPConnection -LocalPort <端口>` 确认当前响应请求的是否是新进程
2. **缓存体检**：检查 jiti cache、session lock、.bak 文件等可能滞留旧配置的位置
3. **重启验真**：重启后必须验证 **PID 已更换**，而不是仅看 health 返回 200

**Why（为什么）**: 
很多看起来像"代码 bug"的问题，根因是**环境态没有刷新**。典型场景：配置文件改了 → 重启服务 → 旧进程没被杀掉霸占端口 → 新进程绑端口失败静默退出 → 旧进程用旧配置继续服务 → 你反复改代码反复不生效 → 误判为代码 bug。这个陷阱的本质是：**你以为在调试代码，其实在跟一个僵尸进程的旧配置对话**。

**Evidence（证据）**: 
[配置不生效调试实例]：配置文件已添加安全放行规则，但服务仍报权限拒绝。经过源码逆向确认代码逻辑无误后，发现旧进程从始至终未被终止——所有 restart 命令都因权限不足无法杀掉 SYSTEM 级进程，新实例因端口冲突直接退出。花了 5 轮重启才意识到问题不在代码而在进程层。用提权终止后，配置立即生效。

**可操作级别**: 🚨 **铁律 (Mandatory)**

> **与陷阱 2 的关系**: 陷阱 2 (Zombie Process) 是本陷阱的一个具体实例。陷阱 4 是更高维度的通用特征——不仅适用于僵尸进程，也适用于缓存残留、session 锁定、配置文件备份覆盖等所有"环境态未刷新"导致的误判。

### ⚡ 高频案例：jiti 编译缓存导致 .ts 修复不生效

**现象**: 修改了 `mcp-bridge.ts`（新增 buffer 残留解析、`\r\n` 标准化等），S24 重启后 Gateway 日志仍然显示旧行为（超时、无 stdout-raw 日志），3 次修复全部"无效"。

**根因**: OpenClaw Gateway 使用 jiti 在运行时编译 `.ts` 插件文件，编译结果缓存在 `%TEMP%\jiti\`（约 20-30MB、500+ 文件）。重启 Gateway 时 jiti 优先加载缓存中的旧编译产物而非重新编译源码。

**强制动作**: 修改 `.ts` 插件文件后，重启前**必须执行**：
```powershell
Remove-Item (Join-Path $env:TEMP "jiti") -Recurse -Force -ErrorAction SilentlyContinue
```

## 陷阱 5: Incomplete Evidence Hallucination (日志不完整导致的幻觉定位)

**What（规则）**: 
在确定分析结论前，**必须先校验日志/证据的完整性**。如果日志存在缺失、截断、层级遗漏，**禁止**基于不完整证据形成结论。必须先补充日志、重新复现，直到证据链完整后才允许定性。

**Why（为什么）**: 
当日志不完整时，Agent（和人类）会不自觉地用"合理推断"填补证据空白。这些推断**看起来像结论**，但本质上是**幻觉**——你并没有看到实际发生了什么，而是脑补了一个"说得通"的故事。基于幻觉的 root cause 分析会导致：修错地方 → 问题未解决 → 反复修 → 越修越乱。多做一次复现的成本远低于在错误方向上调试数小时。

**Evidence（证据）**: 
[多层系统日志截断]：排查数据异常问题时，应用层日志只显示了"收到异常数据"，但没有记录原始报文内容。Agent 基于应用层行为推断是解析逻辑 bug，花了 3 轮修改。最终补充底层日志后发现真实原因是数据在发送端就已截断——应用层收到的本来就是残缺数据，解析逻辑没有任何问题。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 6: 远端依赖无降级链路 (Fail-Open Missing) 🆕

**What（规则）**：
调用远端服务（如 Mem0、向量检索、LLM API）时，**禁止单点依赖**。必须建立三级降级链路：L1 缓存 → L2 存储 → L3 裸上下文放行。

**Why（为什么）**：
远端服务存在网络故障、超时、5xx 等不可控因素。如果单点依赖，远端不可用会导致核心功能全面瘫痪。Fail-Open 是保障系统韧性的底线。

**How（具体步骤）**：
1. 调用远端服务时设置合理超时（建议 3s）
2. 超时/异常后降级到本地缓存（Redis）
3. 缓存 Miss 降级到本地存储（PG/SQLite）
4. 全部失败 → **Fail-Open 放行**，使用当前上下文继续
5. 每次降级必须记录 metric + Warn 日志

**Evidence（证据）**：
[Mem0 记忆架构重构 2026-03-25]：原生架构的 `user_memory.go` 有 Redis 缓存层，但缺乏 Fail-Open 明确定义。重构方案明确提出"三级降级：Redis 缓存 → PG 存量 → 裸上下文"，确保任何远端故障不阻断对话。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 7: 高频远端投递无背压 (Backpressure Missing) 🆕

**What（规则）**：
异步写入远端服务时，**禁止逐条同步投递**。必须使用带背压的队列 + 批量合并机制。

**Why（为什么）**：
远端服务（如 Mem0）每条输入可能触发多次 LLM 调用。高频逐条投递会导致：
1. API 费用和延迟激增
2. 远端服务被打爆
3. 投递失败时消息丢失

**How（具体步骤）**：
1. 创建带容量的 Go channel（建议 100）
2. 投递消息时使用 `select + default` 模式
3. Worker 按 UserID 维度批量合并（建议 5 条）
4. 设置批量刷新间隔（建议 10s）
5. 通道满时执行 `drop` + Warn 日志

**Evidence（证据）**：
[原生架构 vs Mem0 对比 2026-03-25]：原生 `user_long_memory` 有 Worker Pool + `default:drop` 背压机制，这是"抗压能力碾压级优势"。重构方案明确保留此机制："投递失败（通道满）→ `default: drop` + Warn 日志"。

**可操作级别**: 🚨 **铁律 (Mandatory)**

## 陷阱 8: 职责越界导致的架构熵增 (Role Violation) 🆕

**What（规则）**：
工作流/技能之间的职责边界必须清晰。**严禁一个角色处理另一个角色的专属事务**。

**Why（为什么）**：
当 M4（对外拓荒）被迫处理 M5（对内清扫）的事务时：
1. 核心职责被稀释，影响主业效率
2. 专业不对口，处理质量下降
3. 问题归属模糊，排查困难

**How（具体步骤）**：
1. 明确定义每个角色/技能的职责边界
2. 在入口处设置红线拦截
3. 收到不属于自己职责的请求时 **直接拒绝 + 退回**
4. 定期审计，发现越界行为立即修正

**Evidence（证据）**：
[W9/M4/M5 职责重构 2026-03-25]：W9 将 `context_bloat` 抛给 `issues.md`，导致 W7/M4 被迫"代切盲肠"。修复方案：W7 在 Step 2 新增红线拦截："如果传入日志涉及肥胖与死链，W7 必须直接拒绝处理并向 M5 退回"。

**可操作级别**: 🚨 **铁律 (Mandatory)**



## ❌ 陷阱：双通道消息系统不能靠位置或前缀启发式判轮次 [ADDED]

- **现象**：同一轮回复被渲染出两个几乎相同的 Assistant 气泡，常见于一条通道快、一条通道慢，且用户中途打断时。
- **根因**：两个输入通道都拥有“创建新气泡”的权限，但系统没有轮次级别的签收凭据，只拿“最后一项是不是 user”或“文本前缀像不像”这种弱条件做判断。
- **正确解法**：给上一轮气泡挂一个确定性的签收字段，再根据“是否已签收”决定合并还是新建。本次案例里用的是 `mqttFullText`；本质上它是**轮次收据**，不是字符串补丁。
- **执行要点**：
  1. 快通道/慢通道的所有入口都要共用同一套归属规则，不能只修其中一个入口。
  2. 先判断上一个 Assistant 是否已签收；未签收就回填，不要另起炉灶。
  3. 时效窗口只能做容错，不能替代签收凭据。
  4. 排查这类问题时，先问“谁有创建权、谁负责签收、谁负责封口”，再改代码。

## ❌ 陷阱：同一对象的路径字段只修一半，会把恢复流程打白屏 [ADDED 2026-05-21]

- **现象**：Codex++ 会话列表点击后先报 `cannot resume running thread ... stale path`，修掉 `rollout_path` 后弹窗消失，但点击会话仍然白屏。
- **根因**：`state_5.sqlite.threads` 里同一个会话对象不止一个路径字段。`rollout_path` 已从 `\\?\C:\...` 清回普通 `C:\...`，但 `cwd` 仍保留 `\\?\C:\...`。前端恢复会话时继续读取 `cwd` 初始化工作区，旧壳在渲染阶段被这个长路径前缀打挂。
- **正确解法**：路径规范化必须覆盖同一恢复链路里的所有同语义字段，不能只盯住报错里出现的字段。本次修复同时处理 `threads.rollout_path` 和 `threads.cwd`，并把触发器方向改成“去掉 `\\?\` 前缀”，而不是给普通路径加前缀。
- **执行要点**：
  1. 看到 `stale path` 这类字符串比较错误，先查数据库里同一对象的所有 path/cwd/workspace 字段。
  2. 调用方用普通 `C:\...` 比较时，存储层也必须保持普通 Win32 路径；不要用 `\\?\` 长路径前缀做持久化口径。
  3. 修复 watcher/trigger 后，必须清理既有脏数据，再验证未来 insert/update 不会写回旧格式。
  4. 验证不能只看弹窗消失。必须执行真实 UI 动作：重开应用、点击同一个会话、确认不白屏。
- **证据**：
  - `rollout_path_prefixed=0`
  - `cwd_prefixed=0`
  - `PRAGMA integrity_check=ok`
  - `Test-CodexPlusPlusSessionPaths.ps1` 通过
  - 用户复测确认“确实修复了”
