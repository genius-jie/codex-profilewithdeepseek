## 2026-08-28 Codex++ 桌面入口锁死 + 启动后卡住点不动

- **现象（两段）**：① 双击 `Codex++ 启动.lnk` 完全没反应，实例进程树还活着；② 当天晚些时候实例窗口在、但点击无反应。
- **误判点 1（唤醒≠复活）**：见"进程树还活着"就只做窗口唤醒。窗口确实唤出来了，但渲染器已假死，界面点不动——唤醒只解决"窗口被藏起来"，不解决"实例已病"。
- **误判点 2（Responding 不可信）**：`Process.Responding=True` 曾被当作健康证据。实测卡死实例全部 `Responding=True` 且窗口句柄非 0；它只证明消息泵活着。
- **误判点 3（守卫与清理名单不同步）**：守卫 `ownedProcessNames` 认得 `node.exe`，但 kill allowlist 里没有，导致"守卫看得见的进程杀不掉"，孤儿 cua_node 对长期残留。两份名单必须同步演进。
- **真实根因 1（锁死）**：守卫把假死僵尸算作"已在运行"就提前 `exit 0`，脚本里设计好的 stale-kill + 重启恢复路径永远走不到，用户被永久锁在门外。
- **真实根因 2（卡住）**：CPU 失控空转。实测主窗口进程累计 85354 秒 CPU、某子进程 183012 秒（≈50.8 小时），而进程刚启动不久——多核满速空转，渲染器没有余力响应点击。等待无效。
- **修复动作**：`Start-CodexPlusPlus.ps1` 守卫改三态（未运行→启动；可唤醒→唤醒后退出，健康实例绝不杀；唤不出窗口→落入设计内清理并重启），新增 `-Restart` 强制整树清理重启；kill allowlist 补 `node.exe`、`codex-code-mode-host.exe`。
- **验收证据**：`-Restart` 实测清掉 21 个 ++ 进程（含此前杀不掉的 node/node_repl ×8 与 codex-code-mode-host），新实例主窗口 CPU 从 85354 秒降到 8.7 秒；Protect 审计 0 failures（计数 3/2/1 完整）；SessionPaths / SqliteBoundary / ColdSessionReader / ProfileAliasBoundary / Injection 全绿；原生 Codex 12 进程全程零波及。
- **安全边界**：清理只认 `store-apps\` 路径前缀，且复用脚本内既有边界函数（包目录 + WMI Name 与物理文件名双校验）。禁止按进程名匹配杀 `ChatGPT.exe`——原生实例同名，会误杀用户正在用的 Codex。
- **副作用（每次全新启动后复现）**：Codex++ 应用启动时会在自己 profile 的开始菜单重建直连快捷方式 `...\CodexPlusPlusProfile\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\ChatGPT.lnk`，目标是 store 内 `app\ChatGPT.exe` 且**不带任何参数**——双击它会不带 `--user-data-dir` 起进程，破坏 profile 隔离。`Protect-CodexPlusPlusGovernance.ps1` 会报 `Direct Codex++ store shortcut bypasses the controlled launcher`。处置：确认目标位于固定 store 内且非 reparse point 后删除该 lnk；用户唯一入口始终是桌面 `Codex++ 启动.lnk` → Proxy.cmd。这不是启动失败，重启后审计报此项属预期，删掉即恢复 PASS。
- **遗留**：CPU 失控的上游模块未定位。反复出现时需在发生当时抓线程栈，不得把"定期重启"当修复。

## 2026-05-20 Codex++ 看守守护进程（Auto-Repair Watcher）物理注册与健康检测诊断失效

- **现象**：在 Codex++ 仪表盘中，自动自愈看守进程（Auto-Repair Watcher）处于红色异常状态，提示 "not ready"，伴随 2 个错误（Error）和 1 个警告（Review）。在执行安装命令 `codexplusplus install` 时遇到 `EBUSY: resource busy or locked` 阻断，或 robocopy 无响应挂起。
- **误判点**：以为仅凭常规杀死 Codex 单个进程就能解除锁定，或者以为 robocopy 挂起是普通的路径未找到。
- **真实根因**：
  1. **EBUSY 锁定**：除了原生的 `Codex`、`codex` 进程外，后台常驻的辅助管理服务 `codexmanager-service`、`codexmanager-start`、`codexmanager-web` 会一直锁定 `AppData\Local\codex-plusplus\store-apps` 下的目录句柄。同时 Electron-builder 的 Electron 进程或未完全退出的 node 进程也会持有锁，导致 rmSync / rmdir 抛出 EBUSY 异常。
  2. **schtasks.exe 引号参数转义陷阱**：在 Node 中调用 `execFileSync` 执行系统 `schtasks.exe` 创建计划任务时，手动在参数两端添加 `\"` 双引号，而在 Windows 中如果路径末尾是反斜杠（如 `watcher.cmd\`），反斜杠会把双引号转义为字符双引号（`\"` 变为 `\"` 后实际传参为 `watcher.cmd\"`），导致 `schtasks` 无法识别，抛出 `Invalid argument/option` 错误。
  3. **Robocopy 无限重试死锁**：在克隆具有系统强 ACL 保护的 WindowsApps 目录下的 Centennial Store App 文件时，如果遇到锁定或受保护文件，`robocopy.exe` 默认会进行 1,000,000 次重试，每次间隔 30 秒。这会导致 Node 的同步进程调用发生永久挂起无响应。
  4. **健康检测 TaskName 不一致**：Installer 注册的间隔任务名称为 `codex-plusplus-watcher-interval`，然而健康监控模块 `watcher-health.ts` 中却硬编码去查询已废弃的 `codex-plusplus-watcher-hourly`，导致即便定时任务成功注册，前端依然检测为 error 状态。
- **修复动作**：
  1. **彻底杀灭占用**：在安装和维护动作前，彻底强行杀死所有相关的后台进程（`Codex`, `codex`, `codexmanager-service`, `codexmanager-start`, `codexmanager-web`）。并且在 `mirrorDirectory` 中对 `rmSync` / `cpSync` 采取防御性的 `try-catch` 捕获，在主 app.asar 已经成功写入的前提下忽略非核心占用锁导致的异常。
  2. **移除冗余的物理引号转义**：去除了 `watcher.ts` 中传递给 `execFileSync` 的冗余引号包裹，将路径中的反斜杠统一转正，利用 Node 底层原生且安全的自动传参打包，彻底消灭转义双引号 Bug；并补全了非管理员身份运行下使用 `Start-Process schtasks.exe -Verb RunAs -WindowStyle Hidden -Wait` 的 UAC 提权容错。
  3. **限制 Robocopy 重试极限**：在调用 `robocopy.exe` 命令时，强制追加 `"/R:1"` 与 `"/W:1"` 参数，遇到锁定或受限文件时在 1 秒内重试 1 次即快速失败退出，防止进程挂起死锁。
  4. **同步监控命名 SSOT**：同步更新 `packages/runtime/src/watcher-health.ts` 的查询键为 `codex-plusplus-watcher-interval`，与 Installer 保持绝对对齐。
- **验收证据**：
  1. 运行 `Get-ScheduledTask -TaskName "*codex*"`，输出中 `codex-plusplus-watcher` 和 `codex-plusplus-watcher-interval` 均为 `Ready` 状态。
  2. 运行 `codexplusplus status` 和 `doctor`，均输出 `All checks passed` 且 `watcher: scheduled-task`。
  3. 后台无多余占用进程，Codex++ 控制台 Dashboard 健康大屏全部转绿为 "OK"。

## 2026-05-20 Windows 计划任务运行批处理（.cmd）导致的控制台黑窗口闪烁骚扰问题

- **现象**：在 Windows 任务计划程序中，以当前用户（Active Interactive Session）身份每隔一段时间自动触发执行 `.cmd` 批处理文件（如 `watcher.cmd`），系统每次都会强制弹出一个 cmd.exe 命令行黑窗口，闪烁一下然后退出，打扰用户的日常开发。
- **误判点**：以为仅能依靠将任务设为“不管用户是否登录都要运行”（Run whether user is logged on or not）来将其打入 Session 0（需要输入并保存 Windows 账户密码），或者以为必须使用 NSSM 服务进行重度常驻改造。
- **真实根因**：Windows 计划任务机制在运行 `.cmd` / `.bat` 或控制台程序时，如果是以交互登录用户身份运行，会默认拉起控制台宿主（conhost/cmd.exe）展示窗口。而对于定时脚本，使用 NSSM 服务会无意义常驻占用内存，且容易被杀毒软件误杀。
- **修复动作**：
  1. 采用零开销、零干扰的**“VBS 脚本静默代理”**方案。在 `watcher.cmd` 同级目录下生成一个 VBScript 代理脚本 `watcher.vbs`：
     ```vbs
     Set WshShell = CreateObject("WScript.Shell")
     WshShell.Run "cmd.exe /c """ & WshShell.ExpandEnvironmentStrings("%APPDATA%") & "\codex-plusplus\bin\watcher.cmd""", 0, False
     ```
     （使用 `WshShell.Run` 且将窗口风格设为 `0` 代表 100% 隐藏运行）。
  2. 修改 `watcher.ts`，在 `windowsWatcherTaskCommand` 中同时自动写入 `watcher.cmd` 和 `watcher.vbs`，并让其直接返回 `vbsPath`（由于系统默认关联，计划任务执行 `.vbs` 会自动用 `wscript.exe` 静默隐形调起它）。
- **验收证据**：
  - 定时任务配置中的 Action 路径成功指向 `watcher.vbs`。
  - 任务被手动触发时，完全隐形后台运行，没有任何控制台或 cmd 黑窗口闪烁弹出。

## 2026-05-20 Auto Follow-up 自动连击插件主进程崩溃与 UI 渲染挂载 Bug

- **现象**：在 Codex++ 代理模式下，`com.lobster.auto-follow-up` 自动连击插件无法启动，日志中抛出致命错误 `tweak com.lobster.auto-follow-up failed to start: {}`，且设置界面中的重置计数功能渲染显示不全。
- **误判点**：容易盲目怀疑是插件由于 `manifest.json` 配置错误导致无法被加载，或者怀疑是 API 认证秘钥不匹配。
